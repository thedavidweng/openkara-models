# OpenKara artifact catalog contract

This repository is the single source of truth for every model and ONNX Runtime
artifact consumed by the OpenKara app. The contract has two layers:

1. **Immutable release manifests** — one per infrastructure release, content-addressed,
   never mutated after publication.
2. **Stable-channel pointer** — a tiny document that advances only after every
   referenced manifest, asset, and release gate passes.

OpenKara must validate the schema instead of embedding a second Rust-only
interpretation. It must reject incompatible target/runtime/model combinations
using the explicit compatibility edges rather than inferring from version
strings.

## Schemas

| Document               | Schema file                          | `schema_version`                  |
| ---------------------- | ------------------------------------ | --------------------------------- |
| Release manifest       | `catalog/schema-release-v1.json`     | `openkara.catalog/release-v1`     |
| Stable-channel pointer | `catalog/schema-channel-v1.json`     | `openkara.catalog/channel-v1`     |

Both are JSON Schema (draft 2020-12). Field-level structure is enforced by the
schema; cross-field invariants (referential integrity, immutable URLs,
target/provider consistency, generation monotonicity) are enforced by
`scripts/catalog_model.py` and invoked from `scripts/validate_catalog.py`.

## Validation

```bash
python scripts/validate_catalog.py catalog/releases/<release-id>.json
python scripts/validate_catalog.py --schema channel catalog/channels/stable.json
python scripts/validate_catalog.py --all-fixtures
```

`--all-fixtures` validates every document under `catalog/fixtures/valid/` (must
pass) and `catalog/fixtures/invalid/` (must fail, checked against the sibling
`<name>.expected.json` sidecar). Fixtures are generated by
`scripts/generate_catalog_fixtures.py`; never hand-edit them — edit the
mutation table and regenerate.

## Release manifest

A release manifest describes every model, runtime, and bundle artifact
published together, plus the compatibility edges and supply-chain references
that gate stable promotion. Required top-level fields:

- `schema_version`, `release_id` (`YYYY-MM-DD-NNN`), `generation` (monotonic),
  `created_at`, `producer` (repo + commit SHA + workflow + run id).
- `artifacts.{models,runtimes,bundles}` — typed artifact objects.
- `compatibility[]` — explicit model/runtime/target/provider edges.
- `supply_chain` — release-level SBOM, license, notice, provenance refs.
- `gates` — quality, performance, and compatibility report refs (issue #21).

### Artifact identity

Every artifact carries a stable `artifact_id` that **must not be reused for
different bytes**. Deprecation replaces an ID with a new one; it never silently
reuses the old ID. A deprecated artifact records `replacement_artifact_id`
(must exist in the same release) and an optional `sunset_generation`.

### Immutability

`download_url` and the channel `release_manifest_url` must be immutable HTTPS
URLs containing a release tag or content-addressed (40/64 hex) segment. Mutable
"latest"-style URLs are rejected. Every referenced file carries a byte size and
SHA-256 (`archive_digest` plus per-file `extracted_file_digests`).

### Model artifact

Declares `profile` (`balanced` / `quality` / `karaoke_2stem`), `target_triple`
(`null` for portable), `arch`, `os`, and a `model` block with: `format`
(`onnx` / `ort`), `opset`, `ir_version`, `tensor_interface` (`waveform` /
`spectral-core`), input/output semantics, `precision`, `segment_frames`,
`sample_rate`, `stem_profile`, `required_operator_config` (optional in v1 —
pre-#19 model releases may omit it; issue #19 PR 2 makes it required for new
releases and back-fills existing ones), and an explicit `compatible_runtime_ids`
list. The app resolves a runtime only through this list — never by parsing
version strings.

### Runtime artifact

Declares `target_triple`, `arch`, `os`, a `runtime` block (version, ORT C API
level, execution providers, companion files, deployment target,
`supported_model_artifact_ids`), and a `toolchain` block (image, compiler, SDK,
deployment target, CMake flags, submodule state). Built from an exact upstream
tag + commit + source lock (issue #19).

### Bundle artifact

Ties one model artifact to one runtime artifact for a specific
`target_triple`, `execution_provider`, `precision`, and `graph_format`. Its
target must match its runtime's target; its provider must be in the runtime's
providers. Only Pareto-optimal bundles are published (issue #22).

## Channel pointers

`catalog/channels/stable.json` references exactly one immutable release
manifest by URL, SHA-256, and size. It advances in one atomic step after every
referenced asset and gate passes. `generation` is monotonically non-decreasing
and must equal the referenced manifest's generation.

`catalog/channels/candidate.json` (same schema, `channel: "candidate"`) is the
pre-promotion channel introduced with the spectral-core generation (issue #23
PR 3): a release whose artifacts must be validated by the paired OpenKara
work across all targets before the stable switch is published here first
(`publish_catalog_release.py --channel candidate`). Candidate publication
never touches `stable.json`; promoting a verified candidate is a separate
`--channel stable` run against the same, already-published release (assets
are re-verified; only the pointer moves). Production consumers follow only
the stable pointer.

## Update detection (consumer contract)

The app's model-update check works exclusively through the stable pointer.
GitHub release tags are storage addresses; the app must never parse a tag,
filename, or URL to infer a version (invariant above).

**Version identity the app persists at install time:**

- the pointer's `generation` (monotonic integer — the catalog version) and
  `release_id`;
- for every downloaded file: its `artifact_id` and `archive_digest`
  (SHA-256) from the manifest.

**Update check algorithm:**

1. Fetch `catalog/channels/stable.json` from the repository's default branch
   (raw URL). It is a few hundred bytes.
2. If `generation` is not greater than the stored generation, there is no
   update. Stop.
3. Fetch `release_manifest_url` and verify `release_manifest_sha256` and
   `release_manifest_size` before parsing.
4. Diff the manifest's artifacts against stored state by `artifact_id` +
   `archive_digest`. Download only artifacts whose digest changed or that
   are new; verify each download's SHA-256 and byte size before use.
5. If a stored `artifact_id` appears with `deprecation.deprecated: true`,
   migrate to `deprecation.replacement_artifact_id` (present in the same
   manifest) and delete the old file after the replacement verifies.
6. Persist the new `generation`, `release_id`, and per-artifact digests.

A file on disk is identified by its recorded SHA-256, never by its name or
embedded metadata; embedded `openkara.*` metadata is diagnostic only.

**Compressed model assets:** a model artifact whose `filename` ends in
`.tar.gz` is an archive, exactly like every runtime artifact.
`archive_digest`/`byte_size` describe the downloaded archive;
`extracted_file_digests` lists the contained `.onnx` file's SHA-256 and
size. The app verifies the archive digest after download, extracts with a
safe extractor (path traversal, link, and size limits — the same rules the
runtime archives already require), verifies the extracted file's digest,
then discards the archive. Raw `.onnx` artifacts have
`extracted_file_digests` naming themselves with the same digest. (Why the
FP32 payload compresses ~35–40%: the pretrained demucs checkpoints are
half-precision, so half the weight bytes are zero mantissas.)

**Release-tag taxonomy (storage only, never version signals):**

| Tag family | Contents |
|---|---|
| `infra-<release-id>` | immutable catalog release: manifest + supply-chain records |
| `model-spectral-v*`, `model-ft-spectral-v*` | converted spectral-core model assets |
| `model-derived-v*` | deterministic derived model assets (dedup, projections) |
| `ort-v*` | ONNX Runtime archives for the five targets |

## Supply-chain generation

`scripts/generate_supply_chain.py --release <release-id>` pins
`supply_chain_generator_version` in the release spec. New specs use version 2,
which identifies the SPDX document as `SPDXRef-DOCUMENT`, matching its
`DESCRIBES` relationship. When copying a historical spec for a new release,
remove the version pin or set it to 2.

Historical specs explicitly pin version 1 to reproduce their published
release-suffixed document IDs and digests. Their original SPDX relationship
mismatch remains in the immutable records; correcting those published bytes
requires a new release ID. The version pin is generator input only and is
not included in the published manifest. CI still regenerates every spec and
verifies supply-chain digests and immutable manifest bytes.

## Historical note

The temporary `latest.json` migration alias (OpenKara PR #165) was deleted after
OpenKara #167/#179 switched every consumer to the stable pointer + immutable
manifest; channel pointers and release manifests are the only contract surfaces.

## Atomic publication

`scripts/publish_catalog_release.py --release <release-id> [--execute]`
publishes a catalog release as an immutable GitHub release and advances the
stable pointer atomically:

Stable execution requires qualified, immutable per-edge evidence and one complete
frozen current-default baseline per target/provider (see the envelope contract
below) **for any model, weight or artifact change**. Missing, duplicate,
placeholder, incomplete or non-finite entries stop execution before network
writes. Candidate publication remains available for collecting evidence.
`validate_release_evidence.py` enforces this prerequisite; measured reports
remain tracked in #21.

A release whose model artifacts are byte-identical to the current stable release
may instead promote under the runtime-only gate described in
`docs/runtime-only-promotion.md`: an external
`catalog/qualifications/<release-id>.json` record, per-edge native old/new
measurements and OpenKara app-integration reports. The strict baseline/corpus
requirement is not waived for model changes, and the runtime-only path fails
closed when any per-edge evidence is missing or unmeasured.

1. **Dry-run (default):** verifies the manifest validates, supply-chain records
   match local files, every referenced artifact asset URL resolves to an
   existing GitHub release asset whose SHA-256 matches the manifest, and
   generation is monotonic. Exits 0 for valid integrity, without qualifying
   release evidence. No `--skip-asset-check`
   escape hatch exists — every asset must be reachable and verifiable.
Pull requests that edit `catalog/channels/stable.json` are additionally checked
by `scripts/verify_stable_pointer_change.py`: the transition must bind the
promoted-from stable release, the release must be published (not a draft), and its remote
`release-manifest.json` asset must exist with the exact local byte size and
SHA-256, and the release must carry
either a committed runtime-only qualification record or strict release
evidence. The dry run alone never authorises a pointer advance.

2. **Execute (`--execute`):**
   1. Creates a draft GitHub release tagged `infra-<release-id>`.
   2. Uploads the manifest + supply-chain files as release assets.
   3. Downloads every uploaded asset and verifies its SHA-256 and size match
      the manifest.
   4. Publishes (undrafts) the verified release.
   5. Advances `catalog/channels/stable.json` to point at the public release.
   Verification failures delete only a draft created by this invocation.
   A failed publication leaves the pointer unchanged and preserves the release
   for retry. A pointer failure preserves the public release.

`generate_catalog_release.py` writes the immutable manifest only. It does
**not** advance the stable pointer — that is the sole responsibility of
`publish_catalog_release.py` after asset verification. This enforces the issue
#18 PR 4 atomicity contract: the stable pointer never references a release whose
assets have not been uploaded and verified.

## Invariants enforced

1. One catalog entry identifies one immutable asset by URL, size, and SHA-256.
2. The stable pointer never references a mutable asset or partial release.
3. Catalog generation is monotonic; `release_id` is unique.
4. Model/runtime compatibility is explicit; the app does not infer it.
5. Unknown required schema fields fail validation (`unevaluatedProperties: false`).
6. A deprecated artifact's replacement must exist in the same release.
7. Bundle target/provider must match its runtime.

## Required vs. optional fields (v1 policy)

v1 requires **identity + integrity** fields for every artifact: `artifact_id`,
`kind`, `variant`, `filename`, `download_url`, `byte_size`, `archive_digest`,
`extracted_file_digests`, `upstream`, and `deprecation`. **Completion fields**
are optional in v1 because the legacy releases included during migration predate
the issues that produce them; each owning issue makes its field required for new
releases and back-fills existing ones:

| Field                          | Owning issue | Becomes required for new releases in |
| ------------------------------ | ------------ | ------------------------------------ |
| `model.required_operator_config` | #19 PR 2     | #19 PR 2                             |
| `supply_chain` (release + per-artifact) | #18 PR 3 | #18 PR 3 (back-filled for 2026-07-20-001) |
| `gates` (quality/perf/compat reports) | #21     | #21 PR 4                             |
| `upstream.commit_sha` + `upstream.source_lock` | #20 | #20                             |

A release that omits a completion field is still a valid v1 manifest; a release
that omits an identity/integrity field is rejected.

### Native qualification vs diagnostics

`validation_failures` rejects every skipped provider, including DirectML/CoreML.
`--allow-skip-no-gpu` only records the observed DirectML C0262002 invalid display
adapter diagnostic; it neither proves hardware absence nor qualifies a release.
Generic DML, missing kernel, driver and CoreML initialization errors remain failures.
Native ORT builds run only through explicit `ORT source build` workflow dispatch;
PR/push still run the lightweight lock, API, packaging and smoke unit checks.

### Stable evidence envelope contract

The three `gates` envelopes below are the strict gate. A byte-identical-model
release may instead use the external runtime-only qualification record; see
`docs/runtime-only-promotion.md`. Both paths fail closed.

Stable `--execute` loads all three `gates` report refs before publication writes.
Each ref binds URL, actual byte length, SHA-256, report ID and schema version;
malformed, missing or changed bytes fail closed. Historical dry-run integrity
checks do not authorize stable promotion. The real corpus and baseline remain
unfrozen; contract unit fixtures are not release measurements.

The three JSON envelopes use `schema_version: openkara.release-{quality,
performance,compatibility}/v1`, `report_id`, exact `release_id`, `generation`,
and `edges`. Each supported manifest compatibility edge must appear exactly
once in each envelope (no extra rows). Every row has `identity` containing the
four manifest edge fields plus `model_digest`, `model_size`, `runtime_digest`,
`runtime_size`, matching the catalog artifact bytes exactly.

- Quality row: `report` (existing release-tier quality schema), `corpus_sha256`
  (exact reviewed `quality/corpus-manifest.json` bytes), `separation` results,
  `baseline_quality_report` and `baseline_runtime_report` (immutable report refs).
- Performance row: `report` (existing release-tier runtime schema),
  `measurement_backend: native-c-api`, and the frozen `benchmark_environment`.
  The old Python suite's ORT_RUNTIMES environment variable does not prove it
  loaded an archive; wheel measurements cannot be labeled native evidence.
- Compatibility row: `status: passed`, exact quality/performance envelope IDs,
  and `native_smoke` with matching archive/model SHA-256 + size, target and a
  successful strict requested-provider result. A diagnostic skip never passes.

Both quality and runtime results must cover every reviewed corpus fixture
exactly once, with matching category/tier and reviewed per-fixture budgets.
The corpus must include licensed immutable real audio, not just synthetic data.
Separation rows cover every real fixture and contain finite `si_sdr_db`,
`sdr_db`, `leakage_db`, `mrstft_loss`, `transient_error`,
`low_frequency_error_db`, `chunk_boundary_error`; worst-case non-inferiority
is required for each metric. All existing correctness/runtime/size budgets
apply; a target-specific candidate must improve size, cold load, warm latency,
peak memory or separation quality, and cannot be Pareto dominated.

`quality/baselines.json.default_artifact_id` selects the current-default
comparison model. One complete baseline per target/provider is required.
Baseline report documents carry their ref's ID/schema, exact model digest/size,
runtime ID/digest/size, target/provider under `identity`, `corpus_sha256`,
`benchmark_environment` and `metrics` equal to the frozen baseline values.
Their downloaded bytes are verified too. This prevents substituting a different
model, runner, corpus, provider or baseline summary.

Read-only qualification: `python scripts/validate_release_evidence.py MANIFEST`.
Reports must be produced by real measurement tooling and attached as immutable
release assets before referencing them; there is no command to manufacture a
passing report from absent hardware, reference stems or measurements.

Runtime package API verification uses the C header at the exact immutable
`upstream.commit_sha`, not a tag-to-API table or a local checkout. New builds
include `onnxruntime_c_api.h` in the digested manifest. Verification fetches
only that small upstream header and fails closed on fetch failure, API mismatch,
or substituted header bytes. Historical packages without the header require a
new candidate build for a strict (model/weight) promotion; this does not rewrite
historical release assets. Runtime-only promotion may measure a historical
stable archive using the committed `ort/pinned-headers.json` closure for its
recorded upstream commit and API level (or the archive's own packaged closure
when present), as described in `docs/runtime-only-promotion.md`; a package
whose header source cannot be verified still fails closed.
